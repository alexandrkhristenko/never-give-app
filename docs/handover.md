# Что осталось сделать руками

Дата: 2026-08-10. Ветка `feature/mvp-completion`, 12 коммитов впереди `main`.

Автоматические проверки зелёные: 113 юнит-тестов, 45 тестов БД, 42 E2E, `tsc`
чист, линтер **без единого предупреждения**, сборка проходит.

**У проекта появился домен: `https://www.never-give.app`.** Apex редиректит на
`www` кодом 308. Именно этот адрес приложение теперь называет своим — он же
должен лежать в Redirect URLs проекта Supabase.

Список стал заметно короче: прод заработал и открылся, а открытое развёртывание
можно проверять — не только просить. Ниже — то, что осталось за человеком.

Инженерная часть остатка лежит отдельно и разобрана по шагам:
[2026-08-10-next-steps.md](./superpowers/plans/2026-08-10-next-steps.md) —
четыре задачи, которые ещё являются работой, а не доступом.

## 1. Переменные окружения

| Переменная | Куда | Зачем |
|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | `.env.local`; на Vercel **необязательна** | Письма подтверждения регистрации, кнопка «поделиться», базовый URL для OG |

Про эту строку раньше здесь было написано «нет, и нужна». Теперь неверно уже
это: на Vercel адрес берётся из `VERCEL_PROJECT_PRODUCTION_URL`, если переменной
нет. Задавать её нужно только под свой домен. Почему это оказалось важно — и
что натворило прежнее умолчание `http://localhost:3000` — в [debt.md](./debt.md) D2.

`SUPABASE_SERVICE_ROLE_KEY` больше **не нужен** — E2E заводит аккаунт через
`DATABASE_URL` (см. [debt.md](./debt.md) B1). Если ключ когда-нибудь появится,
не кладите его в `.env.local`: всё оттуда попадает в серверный рантайм
приложения, а этой роли там быть не должно — она обходит RLS.

**`DATABASE_URL` нужно задать в Vercel руками** — либо иметь `POSTGRES_URL`,
под которым строку кладёт интеграция Supabase. Приложение принимает оба имени
и предпочитает первое; `POSTGRES_URL_NON_POOLING` намеренно не принимается —
это прямое подключение, из Vercel по IPv4 недостижимое. Без любого из них не
работает ничего, что ходит в базу: именно это уронило вход и регистрацию на
проде, см. [debt.md](./debt.md) B8.

Строку берите **транзакционную** (порт `6543`), а не сессионную. Serverless
поднимает много коротких подключений, и сессионный режим их держит.
Транзакционный режим здесь не компромисс, а то, подо что написан `src/db/rls.ts`:
роль и claims ставятся через `set_config(..., true)`, то есть на транзакцию, —
поэтому подключение из пула не уносит чужую роль следующему запросу.

Переменные окружения применяются только при следующем развёртывании.

## 2. Сквозной E2E

Прогоняется целиком: **42 проверки, ни одной пропущенной.**

```bash
npm run test:e2e
```

Тестовый аккаунт заводится через `DATABASE_URL`, а не через Admin API —
сервисного ключа нет и не должно быть. Обоснование и цена этого решения в
[debt.md](./debt.md) B1.

Механика заморозок при этом **уже покрыта** — отдельным набором, который не
требует сервисного ключа, потому что засевает данные напрямую через
`DATABASE_URL`:

```bash
npm run test:db
```

**Сорок пять случаев в пяти файлах** прогоняют настоящие функции DAL против
настоящей базы: списание, правило «всё или нет», идемпотентность,
неприкосновенность текущего дня, начисление на седьмой день, потолок и вызов,
который тратит и зарабатывает одновременно; онбординг, занятость имени, экран
настроек с удалением аккаунта, ограничитель частоты. Вместе с ними проверяются
блокировка `FOR UPDATE`, колоночные гранты роли `authenticated` и политики на
`streak_freezes` — то, чего юнит-тесты чистой функции не достают.

Занятый username **покрыт** — в `npm run test:db`, где второй владелец имени
засевается напрямую. Пункт product-spec §7 закрыт.

Этот же набор поймал два дефекта, которые не видны без живой базы:

- **онбординг был сломан для всех.** Сужение INSERT-грантов в миграции 0002
  верно по замыслу, но Drizzle перечисляет в INSERT все колонки таблицы, а
  Postgres проверяет привилегию на каждую **названную**, даже со значением по
  умолчанию. Регистрация падала с `permission denied`. Миграция 0003 разделяет
  ответственность: грант решает, какие колонки можно называть, политика —
  какие значения допустимы;
- **занятый ник сообщался как неизвестный сбой.** Drizzle оборачивает ошибку
  драйвера и кладёт оригинал в `cause`, поэтому код и имя ограничения читались
  на обёртке и никогда не совпадали.

## 4. OG-картинка в реальных площадках

**Проверено на живом проде, а не на сборке.** `https://www.never-give.app`
отдаёт `og:image` абсолютным адресом на своём домене, маршрут картинки — PNG
1200×630, и все три краулерных User-Agent (`facebookexternalhit`, `Twitterbot`,
`TelegramBot`) получают теги в исходном HTML, без JS. Картинка просмотрена
глазами: цепочка на ней растёт слева направо. До этого адрес вёл на localhost,
см. [debt.md](./debt.md) D2.

Остаётся прогон через сами отладчики Facebook, X и Telegram — им нужен вход в
эти сервисы. Кэшируют они агрессивно, так что делать это стоит один раз и уже
по настоящему домену.

## 5. Известный долг

Не дефекты, а осознанные решения либо мелочи, зафиксированные ревью:

- **Публичный профиль отдаёт HTTP 200** с содержимым «не найдено». Это следствие
  потоковой отдачи динамических маршрутов в Next 16; фреймворк компенсирует
  тегом `<meta name="robots" content="noindex">`, он на странице есть.
  Проверено: удаление `loading.tsx` статус не меняет. То же самое у
  `/dashboard` без сессии — 200 и скелет, без единого поля данных, см.
  [debt.md](./debt.md) C2.
- **Наборы тестов пишут в продовую базу.** `DATABASE_URL` из `.env.local`
  указывает на тот же проект Supabase, что и прод. Ни один набор не удаляет
  строк, которых не создавал, но защита здесь — аккуратность запросов, а не
  изоляция. Отдельный проект Supabase под тесты убрал бы класс целиком.
- ~~**`check_email` не привязан к режиму.**~~ Закрыто. При починке нашёлся
  второй, более крупный дефект, который прятался за зелёным тестом — см.
  [debt.md](./debt.md) A1.
- **Ограничитель частоты различает два отказа.** Раньше недоступность базы и
  исчерпанный лимит давали одно и то же сообщение «Too many attempts». Отказ в
  закрытую остаётся правильным — но человек шёл ждать окно, которого нет, а
  причина была в другом. Теперь исходов три (`allowed`, `limited`,
  `unavailable`), и второй отказ говорит своими словами. Именно на этом
  различии диагностируется B8 из [debt.md](./debt.md).
- **Content-Security-Policy не задан.** Next вставляет инлайновые скрипты, и
  политика, строгая настолько, чтобы приносить пользу, требует nonce на каждый
  запрос через proxy. Политика с `unsafe-inline` даёт видимость защиты без
  защиты, поэтому её нет вовсе. Остальные заголовки безопасности выставлены.
- **Публичная регистрация непригодна для тестов.** Проверено: Supabase
  отклоняет домены `.test` и `example.com`, а затем упирается в лимит частоты.
  Обойти отсутствие сервисного ключа этим путём нельзя.
- **Уязвимости зависимостей.** Продовые чисты. Четыре умеренных — только в dev,
  в `esbuild` через транзитивную зависимость `drizzle-kit`, и советник касается
  dev-сервера esbuild, который проект не поднимает. `npm audit fix --force`
  откатил бы `drizzle-kit` до 0.18.1 ломающим изменением — это хуже проблемы.
  CI проверяет продовые зависимости на каждом прогоне.

## 6. Что появилось после первой передачи

- **CI** (`.github/workflows/ci.yml`): типы, линтер, юнит-тесты, сборка и аудит
  продовых зависимостей на каждый push в `main` и каждый PR. Наборы `test:db` и
  `test:e2e` намеренно исключены — обоснование в самом файле.
- **`.npmrc` с `legacy-peer-deps=false`.** Это значение по умолчанию, и строка
  ничего не меняет — она защищает от глобальной настройки в `~/.npmrc`. Один
  раз это уже сломало CI: lock-файл собрался на машине, где peer-зависимости
  игнорировались, поэтому в нём был поднят `esbuild@0.25.12` (требование
  `drizzle-kit`), хотя `vite@8` объявляет peer `^0.27 || ^0.28`. `npm ci` на
  чистой машине считает peer-зависимости честно, не сходится с lock и падает с
  `EUSAGE`. Локально ошибка не воспроизводилась ровно потому, что та же
  настройка глушила её и при проверке. Настройка машины разработчика не должна
  попадать в общий lock-файл — отсюда файл в репозитории.
- **`_next` добавлен в зарезервированные имена.** Он проходил валидацию ника, и
  профиль мог занять путь, по которому фреймворк отдаёт свои ассеты. Тест теперь
  утверждает, что список покрывает все существующие сегменты `src/app/`.
- **Колонки времени переведены в `timestamptz`** (миграция 0004).
- **`npm run db:prune-test-users`** — сметает аккаунты, оставшиеся от прерванного
  прогона E2E. По умолчанию только показывает; удаляет с `--delete`.

## 7. Добавлено во вторую очередь

- **Заголовки безопасности** (`next.config.ts`): `X-Frame-Options: DENY`,
  `nosniff`, `Referrer-Policy`, `Permissions-Policy`. Раньше не отправлялось
  ни одного.
- **`robots.txt`** (`src/app/robots.ts`). Профили индексируются, всё за сессией
  закрыто. Sitemap намеренно **не** объявлен: перечень профилей был бы публичным
  списком всех аккаунтов и вернул бы то самое раскрытие существования аккаунта,
  которое закрывали в метаданных и OG-роуте.
- **`promises.updated_at` перестал врать** (миграция 0005). Колонка ставилась
  один раз при вставке и больше не менялась. Триггер, а не код приложения:
  иначе значение было бы верным лишь там, где о нём вспомнили.
- **Аудит доступности** (`e2e/a11y.spec.ts`) на каждой странице без сессии, в
  обеих темах, на двух ширинах.
- **Машина состояний формы входа** покрыта E2E без аккаунта
  (`e2e/login-form.spec.ts`) — включая баг с устаревшей ошибкой при
  переключении режима, который раньше знало только ревью.

- [x] Развернуть правки цепочки и адреса. Влито PR #8 и живёт на проде:

      `www.never-give.app`
- [ ] Развернуть остаток этой ветки: разбор отказов входа и правку документации
- [ ] `npm audit` — при установке зависимостей сообщалось о 6 уязвимостях

**Миграции здесь не супабейзовые.** Схемой управляет `drizzle-kit`, журнал
лежит в `drizzle.__drizzle_migrations`, накатывает `npm run db:migrate`.
Каталога `supabase/` в проекте нет и не было. Поэтому `supabase db push`,
`supabase link` и вкладка миграций в панели Supabase отвечают
`relation "supabase_migrations.schema_migrations" does not exist` — они ищут
свой журнал, которого проект никогда не заводил. Это не пропавшая миграция:
на рабочей базе накатаны все восемь, функции из 0006 и 0007 на месте.

**`npm run db:push` запускать нельзя.** Команда сравнивает схему с живой базой,
не видит политик RLS из рукописных миграций и снесёт их, оставив гранты — то
есть откроет приватные обещания анониму. Скрипт намеренно заменён на отказ.

## 9. Один аккаунт без профиля

В базе есть **один** аккаунт `auth.users` — подтверждённый, gmail, заведён
2026-08-06, последний вход 2026-08-09 в 08:26 UTC. Профиля (`public.users`) у
него нет, а значит нет ни обещания, ни отметок.

**Онбординг тут не виноват — это проверено, а не предположено.** Пройден
насквозь на живом проде с засеянным аккаунтом: вход, `/onboarding`, живая
проверка ника («Available.»), отправка — профиль и обещание созданы, дашборд
открылся. Подсказка адреса при этом читалась как `www.never-give.app/username`,
то есть на верном домене.

Инструменты проекта профиль не удаляли: каждое удаление в `db/`, `e2e/` и
`scripts/` привязано либо к своему `id`, либо к домену `@never-give.test`. И это
**не** след `DELETE ACCOUNT`: функция удаляет `auth.users where id = auth.uid()`,
то есть после успешного удаления не осталось бы и строки логина.

Остаётся одно объяснение: онбординг не был доведён до конца. Войдите и
завершите его. Если он всё же упадёт — журнал Vercel назовёт причину: ошибки БД
пишутся строкой JSON с кодом и именем ограничения.

**Когда завершите, посмотрите на таймзону в `/settings`.** Обход нашёл там
дефект (D4): отправка формы, опередившая гидратацию, создавала аккаунт в `UTC`
молча. Теперь такой случай пишет в журнал `onboarding.timezone_absent`, но у
аккаунта, заведённого раньше, зона могла остаться неверной. Экран настроек
покажет «This device reports …» рядом с сохранённым значением — если они
расходятся, поправьте, иначе граница суток будет не ваша.

Все пробные аккаунты, которыми шли проверки, из базы удалены; `public.users`
пуст.
