# Известные проблемы и технический долг

Дата ревизии: 2026-08-06, коммит `e18f47a`.

Разделено на две части: **дефекты текущего кода** (чинятся планом
`docs/superpowers/plans/2026-08-06-mvp-completion.md`) и **осознанный
техдолг** (не чинится в MVP, зафиксирован намеренно).

---

## Часть 1. Дефекты текущего кода

### 1.1. `redirect()` внутри `try/catch` не работает — КРИТИЧНО

`src/app/dashboard/page.tsx`

```ts
try {
  ...
  if (!dbUser || !dbUser.username) {
    redirect('/onboarding');      // бросает управляющее исключение
  }
  ...
} catch (e) {
  dbUser = { username: 'player1', ... };            // перехватывает его
  dbPromise = { title: 'Set up your database first!' };
}
```

`redirect()` в Next.js реализован через исключение. Блок `catch` его глотает.

**Наблюдаемое поведение:** новый пользователь, вошедший через OAuth, вместо
онбординга видит фейковый дашборд с ником `player1` и текстом
`Set up your database first!`. Онбординг недостижим.

### 1.2. Стрик считается по UTC, а не по таймзоне пользователя — КРИТИЧНО

`src/app/dashboard/page.tsx`, `src/app/[username]/page.tsx`

```ts
const todayStr = now.toISOString().split('T')[0];   // UTC
```

При этом факт «отметился сегодня» на дашборде считается иначе:

```ts
const formatter = new Intl.DateTimeFormat('en-CA', { timeZone: dbUser?.timezone ... });
```

Внутри одной страницы сосуществуют два разных «сегодня».

**Наблюдаемое поведение:** пользователь в UTC+3 после полуночи по местному
времени видит обнулённый стрик, хотя чек-ин был. У пользователей западнее UTC
симметричная ошибка в другую сторону.

### 1.3. Дублирование `calculateStreak`

Пятьдесят строк скопированы в `src/app/dashboard/page.tsx` и
`src/app/[username]/page.tsx`. Правка в одном месте не попадёт в другое.
Тестами не покрыто.

### 1.4. Молчаливый провал онбординга

`src/app/onboarding/page.tsx`

```ts
} catch (e) {
  console.error(e);
  // Handle error (e.g. username taken)
  return;
}
```

Занятый username даёт нарушение уникальности → `catch` → `return` → форма
просто ничего не делает. Пользователь не получает никакого сообщения.

### 1.5. Неверная цель конфликта при апсерте пользователя

`src/app/onboarding/page.tsx`

```ts
await db.insert(users).values({ id: user.id, email: user.email!, ... })
  .onConflictDoUpdate({ target: users.email, set: { username, timezone } })
```

Цель конфликта — `email`, а не `id`. Если строка с таким email уже существует
с другим `id`, апсерт обновит её, оставив `users.id` не равным
`auth.users.id`. Это ломает инвариант, на котором держатся политики RLS
(см. [data-model.md](./data-model.md)).

### 1.6. Подмена данных фиктивными при сбое БД

`src/app/dashboard/page.tsx` и `src/app/[username]/page.tsx` при исключении
подставляют заглушки (`player1`, `Read 10 pages`, `avatar_level: 3`). Ошибка
инфраструктуры выглядит как валидный экран. Диагностика в проде становится
невозможной.

В `[username]/page.tsx` дополнительно: `notFound()` вызывается внутри `try`,
и его исключение тоже перехватывается — работает только по совпадению, потому
что в `catch` есть повторный вызов.

### 1.7. Нет миграций

Каталог `drizzle/` отсутствует, схема применялась через `db:push`. История
изменений БД нигде не зафиксирована, воспроизвести состояние на чистом
окружении можно только накатив текущий `schema.ts` целиком. Откат невозможен.

### 1.8. RLS отсутствует

Все запросы идут по `DATABASE_URL` под привилегированной ролью, минуя
политики. Единственная защита — код приложения. Любая ошибка в проверке
владельца означает доступ к чужим данным.

### 1.9. Заморозки не реализованы

`users.streak_freezes_balance` создан со значением `0` и никогда не меняется.
Механика, описанная в [product-spec.md §4.5–4.6](./product-spec.md),
отсутствует полностью. Нет и таблицы для журнала списаний.

### 1.10. Лишняя зависимость `@vercel/og`

`ImageResponse` входит в Next.js 16 как `next/og`. Пакет `@vercel/og` в
`package.json` дублирует то, что уже есть.

### 1.11. OG-картинка без фирменного шрифта

`src/app/api/og/route.tsx`

```ts
fontFamily: 'monospace', // Using fallback for now
```

Расшариваемая картинка — главный канал распространения продукта — выглядит не
как продукт. Шрифт `Press Start 2P` не загружен в `ImageResponse`.

### 1.12. Тестов нет

Ни тест-раннера, ни единого теста. Дефекты 1.1, 1.2 и 1.4 — ровно те, что
ловятся тестами первыми.

### 1.13. README — шаблон от `create-next-app`

Не описывает ни продукт, ни переменные окружения, ни порядок локального запуска.

### 1.14. `avatar_level` показывается, но не растёт

На дашборде и в профиле выводится `Lvl {avatar_level}`, значение всегда `1`.
Формально не баг, но UI обещает механику, которой нет.

### 1.15. `private` не выбирается в онбординге

Селект видимости предлагает только `public` и `unlisted`, при этом код
`[username]/page.tsx` обрабатывает `private`. Расхождение UI и логики.

## Часть 2. Осознанный техдолг

Принято не чинить в MVP. Каждый пункт — решение, а не недосмотр.

### 2.1. Публичный профиль показывает данные до ленивого списания

Списание заморозок происходит только при заходе владельца на дашборд
(см. [product-spec.md §4.7](./product-spec.md)). Пока владелец не зашёл,
публичная страница может показывать стрик, который уже спасён заморозкой или
уже сгорел.

**Почему так:** альтернатива — писать в БД по запросу анонимного посетителя
либо держать cron. Первое — вектор злоупотребления, второе — инфраструктура
ради косметики. Расхождение живёт максимум до следующего входа владельца.

### 2.2. Смена таймзоны сдвигает историю

`checkins.local_date` вычисляется по таймзоне на момент отметки и не
пересчитывается. После переезда в другой часовой пояс граница суток сдвинется,
и стрик может измениться на день.

**Почему так:** корректное решение требует хранить исходную временную метку с
офсетом и пересчитывать всю историю. Для трекера привычек цена не оправдана.

### 2.3. Одно обещание на пользователя

Схема допускает несколько, UI берёт первое (`limit(1)`). Продуктовое решение
ради простоты MVP.

### 2.4. Зарезервированные поля остаются в схеме

`total_score`, `is_premium`, `cadence`, `cadence_count`, `status`,
`checkins.note`, рост `avatar_level`, таблица `followers` — оставлены как
дорожная карта. Помечены в [data-model.md](./data-model.md).

Таблица `followers` защищена включённой RLS без единой политики: пока фичи
нет, доступа нет ни у кого.

### 2.5. Нет rate limiting

Чек-ин защищён уникальным ограничением, но частота вызовов server actions не
ограничена. Для текущего масштаба приемлемо.

### 2.6. Нет мониторинга ошибок

`error.tsx` логирует в консоль. Sentry или аналог не подключён.

### 2.7. `avatar_level` остаётся в выдаче как константа

UI продолжит показывать `Lvl 1`. Убирать не стали, чтобы не переделывать
вёрстку под будущую механику прокачки.
